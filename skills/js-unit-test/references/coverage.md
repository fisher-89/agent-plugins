# 覆盖率采集与判定

阶段 5 用（5a 采集、5b 判定、5c 归因）。目标是在**不改项目脚本、不修改项目配置、不安装新依赖**的前提下，把覆盖率跑出来。

## 前置判断

按顺序检查，命中即停：

```
① 该包的 package.json 里是否已有 coverage provider
   vitest → @vitest/coverage-v8（或 @vitest/coverage-istanbul）
   jest   → jest 自带（根 jest 配置支持 --coverage）
   ├─ 有 → 可采集
   └─ 无 → 不可采集，报告标注「未安装 coverage provider」，不自行安装
② 框架是否有该维度
   bun test 默认只给 lines / functions，无 branches → 按可得维度判定，缺失维度在报告中写「框架不提供」
③ 直接试跑一次，命令失败 → 不可采集，记录 stderr 尾部原因
```

**不可采集的处置**：直接用画像原命令跑到绿，在最终报告里写「覆盖率未采集 + 原因」，然后进入阶段 6。不安装依赖、不改项目脚本与配置。

## 采集命令

在包目录执行，包管理器前缀沿用画像（`pnpm` / `npm` / `yarn` / `bun`）。

| 框架 | 命令 | 说明 |
|---|---|---|
| vite-plus | `pnpm exec vp test --coverage` | 与阶段 5a 同一条命令，仅追加开关 |
| vitest | `pnpm exec vitest run --coverage` | 必须带 `run` |
| jest | `pnpm exec jest --coverage` | 默认单次运行 |
| bun | `bun test --coverage` | 无 branches |

保留 5a 已有的其他开关（如 `--sequence.shuffle`、文件过滤器），只追加 `--coverage`。

**只统计本次范围。** 若配置了 `coverage.include` 等字段，以模块清单的目录为准；必要时用 `--coverage.include=<glob>` 临时收敛，不要修改 `vite.config.ts` / `jest.config.*`。

覆盖率报告目录由测试工具按默认位置生成，不用重定向、不用清理。

## 退出码

项目若在配置里设了 `coverage.thresholds`，未达标会让命令以非零码退出——此时**用例本身是全绿的**。判断方法与处理：

```
输出里有失败用例（FAIL / ✗）        → 按 5a 的用例失败分叉处理
无失败用例但 exit ≠ 0 且带覆盖率摘要 → 只发生了覆盖率门禁失败，继续 5b 判定
```

不要因为这种非零码把测试判成失败，也不要为此改项目配置。

其余无法归入以上两类的非零退出（如 provider 加载报错）→ 去掉 `--coverage` 重跑一次确认测试本身通过，再按「不可采集」处理，记录 stderr 尾部原因。不要为这类报错改项目配置或装依赖。

## 读法与判定

优先读终端摘要表（`% Stmts / % Branch / % Funcs` 或 `% Lines / % Branches / % Functions`），不解析 `coverage/` 下的 HTML。

阈值以 `SKILL.md` 阶段 5b 的表格为准（lines 80 / branches 70 / functions 80），与项目配置里的 `coverage.thresholds` 无关——后者只影响工具是否报错退出，不参与本 skill 的判定。

三个维度全部达标 → 5b 通过。

任一维度不达标 → 进入 5c。**先定位再归因**：

1. 从摘要表下方找未覆盖行号（vitest 的 `Uncovered Line #s` 列；jest 的 `Uncovered Line #s` 同列）
2. 逐段回读源码，判断该行属于：
   - 本应被测到的正常分支 → 流程内
   - 防御性死代码 / 不可达分支 / 需要真机环境 → 环境类
3. 汇总成「文件 → 行范围 → 归因」小表，再按下节分流

## 归因与回补

**流程内问题**——本次补测试的过程有缺口：

| 现象 | 回到 |
|---|---|
| 阶段 2 反构漏了导出或分支 | 阶段 2 |
| 阶段 3 用例表未覆盖该分支 | 阶段 3 |
| 阶段 4 漏生成、或生成的用例走不到该分支 | 阶段 4 |
| 用例写错（断言、mock 掩盖了分支） | 阶段 5a |

回补后从该阶段继续往下走，并重跑 5a、5b。回补上限 **2 轮**（初跑之外最多再补两轮）。

回补到阶段 3 时，`test-design.md` 的改动**照常过阶段 3 出口的用户确认**，确认后再从阶段 4 继续。这条硬约束不因回补而豁免。

**环境问题**——不在本 skill 的可改范围，不改源码，记入最终报告：

- 源码缺陷：死代码、不可达分支、逻辑错误
- 接口定义：该导出的没导出、类型收窄导致分支无法触达
- 模块文档：描述与实现不一致
- 测试环境无法构造：真机、原生依赖、外部服务、jsdom 缺失的浏览器能力

达到回补上限仍低于阈值时停止回补，剩余缺口按上述分类原样写入报告，继续阶段 6。

## 报告格式

阶段 7 里写成一节：

```markdown
## 覆盖率

| 维度 | 实测 | 阈值 | 结论 |
|---|---|---|---|
| lines | 84.12% | 80 | 达标 |
| branches | 68.30% | 70 | 不足 |
| functions | 91.00% | 80 | 达标 |

采集命令：`pnpm -C packages/desktop exec vp test --coverage`

### 未达标归因

| 文件 | 行 | 现象 | 分类 | 处置 |
|---|---|---|---|---|
| src/foo/bar.ts | 120-134 | 错误恢复分支未被触达 | 流程内 | 已回补阶段 3 用例 |
| src/foo/baz.ts | 88 | 依赖原生 WebView 的降级路径 | 环境 | 留待用户 |
```
