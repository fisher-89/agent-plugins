## 1. 问题定义

### 1.1 当前状态

```
PreToolUse Hook 检测 git commit
    ↓
注入 additionalContext: "Consider running code-review..."
    ↓
permissionDecision: "allow"
    ↓
Claude 可能忽略建议直接提交
    ↓
Review 结果不记录，无法追溯
```

### 1.2 目标状态

```
Apply 所有 Task 完成
    ↓
自动启动 Code Review Agent
    ↓
审查结果写入 test-reports/code-review-*.md
    ↓
┌─ 有 ERROR → 阻止提交，提示修复
└─ 无 ERROR → 允许提交，记录通过
    ↓
Commit 带上 review 通过标记
```

### 2.2 持久化逻辑

```python
def save_review_report(change_dir: str, report: str) -> str:
    """Save review report to test-reports/."""
    test_reports = os.path.join(change_dir, "test-reports")
    os.makedirs(test_reports, exist_ok=True)

    timestamp = datetime.now().strftime("%Y%m%d-%H%M%S")
    filename = f"code-review-{timestamp}.md"
    filepath = os.path.join(test_reports, filename)

    with open(filepath, "w", encoding="utf-8") as f:
        f.write(report)

    return filepath
```

### Step 7.5: Automated Code Review

When all tasks are complete and before committing:

1. **Launch Review Agent**

   Use the Agent tool to perform automated code review:
   ```
   Agent tool:
     subagent_type: "general-purpose"
     prompt: |
       Review ALL code changes in the current change '<change-name>'.

       Context files:
       - openspec/changes/<name>/proposal.md
       - openspec/changes/<name>/tasks.md

       Review scope:
       1. Logical errors in implementation
       2. Null/boundary handling
       3. Security issues (injection, auth bypass)
       4. Redundant or dead code

       - List findings as ERROR / WARN / INFO

       - End with verdict: PASS or BLOCK

   Write the review results to:
   `openspec/changes/<name>/test-reports/code-review-<timestamp>.md`

3. **Handle Verdict**

   - If **BLOCK** (any ERROR found):
     - Do NOT proceed to commit
     - Display all ERROR items to user
     - Offer to fix issues or acknowledge and override
   - If **PASS** (no ERROR):
     - Proceed to Step 8 (Auto-commit)
```

### 3.3 防线：Hook 增强

**改造 `pre-tool-commit-review.py`**:

```python
def main():
    # ... (existing detection logic)

    if not is_git_commit_command(command):
        output_result("allow", "")
        return

    # Check if review was already done for this change
    active_change = find_active_change(changes_dir)
    if active_change:
        change_name, change_dir = active_change
        latest_review = get_latest_review(change_dir)

        if latest_review and latest_review["verdict"] == "PASS":
            # Already reviewed and passed
            output_result("allow", "")
            return

        if latest_review and latest_review["verdict"] == "BLOCK":
            # Review found blocking issues
            context = (
                f"Code review found {latest_review['error_count']} ERROR(s). "
                f"Review report: {latest_review['path']}. "
                f"Fix issues before committing, or acknowledge to override."
            )
            output_result("allow", context)
            return

    # No review done yet - strongly recommend
    context = (
        "No code review found for this change. "
        "RECOMMENDED: Run code-review agent before committing. "
        "Use Agent tool to review staged changes."
    )
    output_result("allow", context)
```

## 4. 方案 H：Review 门禁

> **状态**: ✅ 已实现
>
> **实现文件**:
> - `plugin/hooks/pre-tool-commit-review.py` — 安全问题 deny，多次追溯
> - `plugin/agents/code-review.md` — 安全检查项，结构化输出

### 4.1 设计原则

**软约束 vs 硬约束**：

| 约束类型 | 实现 | 适用场景 |
|----------|------|----------|
| 软约束 | `permissionDecision: "allow"` + context | 大多数情况，给开发者灵活性 |
| 硬约束 | `permissionDecision: "deny"` | 严重安全问题时 |

### 4.2 门禁规则

```python
def evaluate_review_gate(review_result: dict) -> str:
    """
    Determine permission decision based on review result.

    Returns: "allow" or "deny"
    """
    errors = review_result.get("errors", [])

    # Always deny for security issues
    security_errors = [e for e in errors if e["category"] == "Security"]
    if security_errors:
        return "deny"

    # Allow but warn for other errors (developer can override)
    if errors:
        return "allow"  # with strong warning context

    return "allow"
```

### 4.3 安全问题硬约束

当检测到以下问题时，`permissionDecision: "deny"`:

| 问题类型 | 示例 |
|----------|------|
| SQL 注入 | 字符串拼接 SQL |
| 认证绕过 | 缺少 auth middleware |
| 敏感数据泄露 | 密码明文日志 |
| 命令注入 | unsanitized input to exec() |

**deny 时的处理**:

```python
context = (
    f"CRITICAL: Security issue detected - {error_description}. "
    f"Commit BLOCKED. Fix the security issue before proceeding."
)
output_result("deny", context)
```

### 4.4 用户覆盖机制

对于非安全类 ERROR，允许用户确认后覆盖：

```markdown
### Override Protocol

If user explicitly says "commit anyway" or "override review":
1. Log override in review report
2. Add override reason to commit message:
   ```
   feat(change): complete implementation

   Review override: <reason>
   WARN-1 acknowledged, deferred to later.
   ```
3. Proceed with commit
```

## 7. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| Agent review 不稳定 | 误报/漏报 | 结构化 checklist + 人工可覆盖 |
| Review 耗时长 | 开发体验差 | 只审查变更文件，设置 120s 超时 |
| 安全 deny 过于严格 | 阻塞合法提交 | 仅限明确安全模式，提供修复建议 |
| Hook 与 Skill 双重检查 | 冗余 | Hook 作为防线，Skill 为主路径 |
