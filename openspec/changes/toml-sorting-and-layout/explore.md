## 摘要

写工具的「插入即追加」会让模型文件的顺序随写入逐渐失去结构。本篇原以为解法是「插入后整体重排」
（一个独立的 `archi_sort` 工具）——实测与源码核查后这个框架被推翻：

**文件序不是「某个工具何时来整理」的时机问题，而是「写面输出必须满足的不变量」。**

理由是 `graph/model/**` 有两条并存的写面（工具 + 自由文本 `write` / `edit`，L3a 双写面是终态），
任何一次性整理都会被下一次自由文本写入打回。故规范化只能焊在**每次写的出口**：`apply_*` 内插
一层规范化，把文件收敛到三条不变量（§1.1）。代价实测极小——全模型一次性规范化的总 diff 只有
`06-frontend.toml` 的 3 个元素块。

而且这三条不变量**与解析无关**（§1.1 逐面核查）：它们是纯文本整洁约束，唯一目的是让
`git diff` 长期保持可评审。这一条定性决定了后续全部取舍——不出诊断、不出 warning、
不进运行时自证链、不设手动入口。

## 一、结论：三条不变量

### 1.1 不变量（全是文本面子，零解析语义）

写入后的模型文件恒满足：

| 号 | 不变量 | 现状 | 解析 / 读数影响 | 说明 |
|---|---|---|---|---|
| **E1** | 父先于子 | 6/6 ✔ | **零** | 现状天然成立（父必须已声明 + 只追加 ⇒ 父必在前）；`orphanHierarchy` 只看声明集合不看顺序（`graph.rs:153-172`）；规范化的 DFS 展开天然产出它，无需独立检查 |
| **E2** | **子树连续** | 5/6 ✔ —— `06` 违 1 处 | **零** | 唯一的实际修复对象 |
| **R1** | **同一 `from` 组连续** | 6/6 ✔ | **零** | 捕获「新关系 append 到 AoT 末尾造成 from 组分裂」 |

三条都取「现状几乎全满足」的形式 ⇒ **规范化对健康文件是 no-op**，只对真错位动手。

**「解析影响 = 零」是本篇的枢纽裁决**（2026-11-25，用户裁定「排序实际对解析无影响，目的仅仅
是长期保持 diff 整洁」）。逐面核查：

| 面 | 顺序依赖 | 锚 |
|---|---|---|
| 结构诊断（四类） | ✘ 集合 / 图论判定 | `graph.rs:137-172` |
| 出线 DTO | ✘ 已 `sort_by(fqn)` | `dto.rs:770-771` / `895-901` |
| 漂移报告条目序 | ✘ 经 DTO（FQN 序） | `drift/mod.rs:118` |
| 结构 diff | ✘ BTreeSet / 多重集合 | `diff.rs:47-60` |
| 契约判据 | ✘ 经 DTO | `api/mod.rs:1045` |
| **行号** | **✔ 变**（`Element.line` / `modelLine`） | 跟着文本走是**正确行为**，不是副作用 |

三条推论（全部写进后续节）：

1. **不进自证链**：规范化的失败模式是「序不对但仍合法」。若在 `finish()` 的运行时自证里断言
   序，美观 bug 就会升级成写入失败（fail-closed 用错了地方）——序由**测试**守，不由运行时守。
2. **不进出线诊断 / warning**：见 §6.1-b 裁决；`DiagnosticKind` 尤其碰不得（`diagnostics`
   非空即画布停摆，而 `06` 当前就有 1 处 E2 违例）。
3. **自由文本通道不算漏网**：它造出的违例会在下一次工具写时被静默修好——这正是「每次写」的
   全部价值。

### 1.2 为什么是「每次写」而不是「某次整理」

`graph/model/**` 有两条并存的写面：工具（`archi_element` / `archi_relation`）与自由文本
`write` / `edit`（L3a 双写面是终态）。任何一次性整理都会被下一次自由文本写入打回，所以
规范化只能焊在**每次写的出口**——这是「文件可能在写入期间被其他途径修改」的直接推论。

由此得到一条没有商量余地的要求：**规范序必须是「最小移动」形式**。若规范化本身要搬掉
半个文件，那它就等于每次写都把 diff 冲成噪声，评审面丢失——而「保住评审面」正是这三条
不变量的**唯一**目的（§1.1：零解析影响）。

### 1.3 规范序的精确定义

元素面 = **DFS + 同层保持首次出现序**：

- 顶级元素按文件内的出现序；
- 某元素的子元素 = 所有 `<父FQN>.` 直接子，按它们**在文件中首次出现的顺序**递归展开；
- 换句话说：唯一被移动的是「不在其父子树连续区间内」的元素，同层相对序原样保留。

关系面 = **组连续 + 组间保持首次出现序**：同一 `from` 的边聚成一段，段的先后 = 该 `from`
在文件中第一次出现的位置，段内的 `to` 序原样保留。

R1 的实际作用点正在这里：新建关系 append 到 `ArrayOfTables` 末尾，若该 `from` 已有组，
文件里就出现两段同 `from` 的边（组分裂）；规范化把末尾那段并回首次出现的位置，组内相对序
保持、新边落组尾。

两条定义共同的性质：**幂等**（同一份输入排两次结果相同）、**序敏感**（同层序由输入决定，
不由字典序决定）。序敏感是刻意的——它保住手排的语义序（§2.3），代价是"两次不同的插入
历史会得到不同的同层序"。

### 1.4 写入语义的变化

```
现状:  读源 → 改 AST（新元素 / 新关系追加表尾）→ 渲染 → 表头回填 → 自证 → 落盘
之后:  读源 → 改 AST（同现状）→ 规范化（重编号 position）→ 渲染 → 表头回填 → 自证 → 落盘
```

三条可感知的后果：

1. **新建元素 / 关系仍 append**，规范化随后把它带到 DFS 位（= 其父的最后一个子之后，
   因为它的"首次出现"就是最后）——**插入点判断消失**；
2. **一次字段修改可能夹带搬家**：首次写到 `06` 时，改一个 `api` 字段的 diff 会带 3 块搬迁（§6.3-1），
   并在响应里由 `reordered.moved = 3` 显式报出（§4.5）；
3. **只要走工具写，文件序必然收敛**——不需要人记得跑什么工具，也没有"忘了排序"这个状态。

## 二、实测：现状与规范化的真实代价

### 2.1 六个文件的现状读数

2026-11-25 实测（脚本按 FQN 前缀重算结构性质）：

| 文件 | 元素 / 关系 | 父先于子 | 子树连续 | 同层字典序违例 | 关系 `(from,to)` 违例 |
|---|---|---|---|---|---|
| `01-app` | 2 / 0 | ✔ | ✔ | 0 | 0 |
| `02-backend-core` | 9 / 10 | ✔ | ✔ | 3 | 0 |
| `03-backend-infra` | 8 / 25 | ✔ | ✔ | 0 | 0 |
| `04-backend-shell` | 1 / 14 | ✔ | ✔ | 0 | 0 |

`06` 的那处断裂是**唯一的结构性错位**：

```
Desktop.Views
  Views.AgentDebug … Views.Changes … Views.Welcome    ← 9 个直接子，Changes 在内
  Views.Changes.Flow / Renderers / Agent              ← ✘ 被追加到整个 Views 组尾（Welcome 之后）
Desktop.Components
```

同层字典序违例明细：

- `02`：`Foundation > Config` · `Workflow > Archi` · `Orchestration > Agent`（**分层依赖序**：
  Foundation → Config → Workflow → Archi 是 core 分层从底到上，确定是语义手排）
- `05`：`ExportBindings > ArchiApiGen`（可能是追加顺序的遗留——`archi-api-gen` 晚于
  `export-bindings` 建）
- `06`：`Views > Components`（语义：视图层先于组件层）· `Views.Changes.Renderers > Agent` ·
  `Components.Standard.Select > Combobox`（后两处无法确证是刻意还是追加遗留）

**这七处在规范序下不会被修复**——它们本身就是「同层首次出现序」，而 E1/E2/R1 三条不变量
不含「同层字典序」。规范化只管子树连续性，手排的同层序一律保留（无论它是有意的还是追加
遗留的）。若将来要清理，只能人工，不在本篇范围内。

关系面 17 处违例里，**14 处是同一 `from` 组内的 `to` 手选序**，模式高度一致：
`X → Desktop.GeneratedBindings` 统一**提前**到 `X → Desktop.Components.*` 之前
（生成物中继边集中组首）。这是有意的语义分组，「组内按 `to` 字典序」会精确摧毁它。

**一条反直觉的推论**：「追加」本身不会破坏「父先于子」——写工具要求新建元素落父元素文件，
且父必须已声明（否则 parser 报 `orphanHierarchy`），加上只追加，父必然排在子之前。追加唯一
能破坏的是**子树连续性**：新元素的父已有后代排在更靠前的位置。`06` 那处正是这么来的。

（注意 `orphanHierarchy` 只判「父是否声明」，不判顺序——所以 E1 不是白送的；只有自由文本
写入才可能把子表搬到父之前，而规范化会把它拉回来。）

### 2.2 规范化的真实代价：3 块

按 §1.3 的定义重排，逐文件比对：

```
01 / 02 / 03 / 04 / 05   目标序 == 现序       零 diff ✔
06                       3 块前移
```

`06` 里移动的只有 `Views` 组这 12 个块（`|` 标出 `Changes` 的边界）：

```
现  … Changes │ Config DbInspector Explores Info Welcome │ Changes.Flow Renderers Agent
目  … Changes │ Changes.Flow Renderers Agent │ Config DbInspector Explores Info Welcome
```

即三个后代从文件的第 12-14 个元素位搬到第 7-9 位（1 起始）——**全部 diff 就是这 3 个
`[element."…"]` 块**。关系面零 diff（现状 6/6 组连续 ⇒ 最小移动即原序）。

这条数据推翻了早期两处估计：原稿猜「序 B ≈ 25 处」，而把序 C 记成「只动插入过的新元素」
——真实值介于二者之间，且恰好只有一处。

### 2.3 仓库里并存两套序（为什么不能选机械序）

| 文件 | 元素序 | 关系序 |
|---|---|---|
| `02-backend-core` | 分层依赖序（Foundation→Config→Workflow→Archi→…） | **纯 `(from,to)` 字典序**（from 组 = Archi / Checks / Config / Orchestration / Workflow） |
| `06-frontend` | DFS + 语义手选（Views 在 Components 前） | `from` 组 = **元素出现序** + 组内手选（`GeneratedBindings` 统一提前） |

**同一仓库同时存在两套互不兼容的序约定**：任何机械序都必然择一并改写另一套的产物。
这是「规范序只能取最小移动形式」（§1.3）的根本理由。典型反例：若 `R1` 定义为
「`from` 组按元素声明序」，`02` 的关系面会被整段重排（它的 `from` 组是字典序）；
只有「组间保持首次出现序」才能让两份文件都零 diff。

另写一份**）。

## 三、`toml_edit` 0.25.15 的实现事实

### 3.1 渲染序 = `(path 非空, position)` + 稳定排序

`src/encode.rs:178-196`：

```rust
let mut last_position = 0;
visit_nested_tables(... |t, p, is_array| {
    if let Some(pos) = t.position() { last_position = pos; }   // 无 position 即继承前表
    tables.push((last_position, t, p.to_vec(), is_array));
});
tables.sort_by_key(|(id, _, path, _)| (!path.is_empty(), *id));  // 稳定排序
```

三条可直接利用的性质：

1. 文本位置 = `(path 非空, position 号)`，root（虚表）恒最前；
2. **稳定排序** ⇒ 同 position 号的一组表，按遍历序（= items 序，IndexMap 保插入序）排列；
3. position 是**纯内部状态**，改它不改任何既有行的字节。

额外收益：把元素区的号恒小于关系区，混插的 `[element.*]` / `[[relation]]` 会被自动理顺。

### 3.2 position 由解析器连续分配

`src/parser/document.rs:456-460`：每遇到一个表头 `current_position += 1` 并写入该表
（root 固定 0）。⇒ 解析出的文件里 position 是 `1..N` 的**连续无洞序列**：

```
文件文本:  [element.A]  [element.A.B]  [element.A.C]  [[relation]]  [[relation]]
position:      1             2              3             4            5
             └──── 元素区 1..k ────┘    └──── 关系区 k+1..N ────┘
```

于是规范化 = **元素区内的一次号重分配（permutation）**：目标序第 `i` 位的元素编号 `i+1`，
关系表编号 `k+1..N`（保持它们的相对序）。新建元素的 position 即便是 `None`（渲染时继承前表号）
也无妨——它随后会被这次重编号覆盖。

### 3.3 不能用的 API：`sort_values_by`

`Table::sort_values_by` 的文档原文：*"This sorts the syntactic table (everything under the
`[header]`) and not the logical map of key-value pairs. **This does not affect the order of
sub-tables or sub-arrays.**"* —— 而 `[element."X"]` 正是 `element` 表的**子表**，所以这条
API 对元素序无效（早期「配一张键序索引后 sort_values_by」的方案因此作废）。

### 3.4 可用的 API：`ArrayOfTables` 的 `insert` / `replace` / `remove`

关系面按 R1 重排需要真移动 Vec 成员（`insert(index, table)`），不能只靠 position ——
否则 Vec 序与 position 序打架。

### 3.5 decor 不用单独处理

既有表之间是「上一行尾 `\n` + 本表 prefix `\n`」= 一个空行，`Table::new()` 的默认
`DEFAULT_TABLE_DECOR = ("\n", "")` 恰好同款（`new_relation_table` 里显式 `set_prefix("\n")`
也只是同一口径）——所以表在文本里换位不会多出或少掉空行。

## 四、实现落点

### 4.1 四个面

| 面 | 手段 | 备注 |
|---|---|---|
| 元素表序 | 目标序算好后在元素区**重编号 position**（区间内连续分配） | 改内部状态，不改既有字节；同号按 items 序 |
| 关系表序 | `ArrayOfTables` 按 R1 重排 Vec（成员迁回组尾，组间相对序不动）+ 重编号 position | 两处同时动，否则 Vec 序与 position 序打架 |
| 反馈面 | `WriteOutcome` 加 `reordered`（§4.5） | 唯一新增出线字段；工具响应加一行 |
| 渲染 | 既有 `finish()` 链原样：渲染 → 重解析 → 表头回填 → 重解析自证 → 回读 | 规范化插在 `apply_*` 内、`finish()` 之前；**自证链不加序断言**（§1.1-1） |

### 4.2 与 `expect` / `hash` 的关系

零影响：`expect` 校验的是**写入前**文件当前哈希（`check_expect`），`hash` 由
`file_hash_of(&file, content)` 在文本定稿后算（`drift/mod.rs:625`，逐字等于落盘后的
`file_hash`）。规范化落在 `apply_*` 内部 ⇒ 在两环之间，不动这条链。

### 4.3 零额外 IO

`plan_element_upsert` 手里已有 `Model`（含全文件元素序与 `line`）与 `source`，
序计算是纯内存判断；规范化不引入任何新读盘、新子进程、新 Tauri 依赖。

### 4.4 知识骨架必须同批改一句（预算很窄）

`crates/infra/agent/src/archi-knowledge.md` 里现有一句现状承诺：

> 工具表达不了的（**重排** / 批量整理）才手改 TOML，改完必须 `archi_module` 自查。

规范化落地后「重排」不再需要手改，这句必须改（否则直接把 agent 引向手排）。硬约束：

| 约束 | 实测 / 出处 |
|---|---|
| 骨架门限 ≤ **1500 B**、全文 ≤ **1700 B**（`lf_bytes(trim_end)`） | 主篇 `design.md`（AC-11，实测值冻结） |
| 骨架当前 **1459 B**（磁盘字节） | ⇒ **净增预算仅约 41 B** |
| 「手改出口一句」有语料测试逐句断言 | 主篇 AC-11 同条 |
| 零结构诊断词（`orphanHierarchy` / `dependsOnAncestor` 等） | 同上 |

⇒ 现实做法是**删字而非加字**：把「（重排 / 批量整理）」收成「批量整理」即可腾出空间，
无需新增句子（规范化是写工具的默认行为，本不需要 agent 知道）。

### 4.5 `reordered` 的形态与文本上限

**裁决**（2026-11-25）：**加**，且**要设计文本上限**。

形态照仓库既有的「计数优先 + 清单有界」惯例（`archi_api` 的 `findings: { total,
byCategory, items }`、db 工具的 `total` / `matched` / `returned`）：

```json
"reordered": { "moved": 3, "blocks": ["Desktop.Views.Changes.Flow", "Desktop.Views.Changes.Renderers", "Desktop.Views.Changes.Agent"] }
```

| 字段 | 语义 | 上限 |
|---|---|---|
| `moved` | 本次顺带挪动的**最小块数**（0 = 无重排，健康文件的常态） | 天然有界（`usize`）；**永不被 cap 截断** |
| `blocks` | 各移动块的**首元素 FQN**（元素面）/ **`from` FQN**（关系面），按文件序 | **cap = 8 项**，超出即截断（`moved` 仍给真值） |

设计依据：

- **cap = 8**：`WRITE_LIMITS.fqn = 256 B` 是 FQN 极值 ⇒ 最坏 `8 × 256 ≈ 2.0 KB`，占
  `MAX_RESULT_BYTES = 50 KB` 硬闸的 4%；典型 FQN（~30 B）下约 240 B。
- **截断不加「…等 N 项」文本**：`moved` 已在场，再加省略文本是重复。这与 `cap_result`
  （字节硬闸的兜底、必须在文本里留痕）不同——这里是**字段级设计 cap**，不是兜底。
- **取前 8 不取后 8**：人读 diff 从上往下，前 8 项与 diff 的首批 hunk 对得上。
- **`moved = 0` 是主路径**：健康文件上规范化是 no-op，故响应恒为
  `{"moved":0,"blocks":[]}`（21 B）。**MUST NOT 因零值省略该字段**——与既有「投影不补
  默认值 / 显式字段不省略」同款。

块的口径（元素面）：规范化只在「子树不连续」处动手 ⇒ 移动块 = 那些「父已有后代排在更前
位置」的元素所领的连续段。`06` 的案例：3 块（`Flow` / `Renderers` / `Agent` 各一块）。
算法细节归 design 阶段；口径定死为**最小移动块**（不是「位置变化的元素数」——后者会把
`06` 报成 8）。

关系面同形：R1 只做组连续化、组内序不动 ⇒ 移动单位恒是「整段」，`blocks` 放该段的 `from`
FQN 即可。

### 5.1 两次形态裁决

| # | 裁决 | 影响 |
|---|---|---|
| 1 | 走 S4'（写工具内定位），不做独立 `archi_sort` 工具 | 形态从「新增工具面」缩到「写工具内部改动」 |

第 2 条的理由即其括注：两条写面并存，任何一次性整理都会被下一次自由文本写入打回。

（三条细节裁决 a / b / c 见 §6.1。）

### 5.2 作废的候选与死因

| 候选 | 死因 |
|---|---|
| **S2 写后自动重排整个文件** | 早期判「diff 被重排污染、评审面丢失」——**后由裁决 2 反转**：只要规范化只做最小移动（§1.3），diff 就不是「整个文件重排」而是 `06` 的 3 块 |
| **S3 独立 `archi_sort` 工具**（`scope = file / all`） | 裁决 2 后失去存在理由：全量规范化由任意一次写顺带完成。且 `scope = all` 天然是 N 文件产物，与单文件写面（`ModelWrite` / 单文件 `expect` / 单点 `write_atomic`）冲突；**§6.1-c 再判「手动入口一律不要」**（连只读预览形态也否） |
| **S4 插入即定位**（锚 = 父的最后一个后代） | 裁决 2 后不需要：整份文件每次写后收敛到规范序，插入点判断消失。且它有个硬伤——**会继承历史错位**（`06` 的断裂区里新建 `Changes.*` 会一直跟着错位走，因为锚取的是「父的最后一个后代」=`Changes.Agent`，而它在断裂区里） |
| **`sort_values_by` + 键序索引** | API 不管子表（§3.3） |
| **纯字典序**（FQN / `(from,to)`） | 会把层级骨架压平（`Desktop.Components.*` 全部排到 `Desktop.Shell` 前），且摧毁人工语义序（§5.3） |

### 5.3 刻意不选的序规则

| 规则 | 现状违例 | 死因 |
|---|---|---|
| 同层字典序 | 7 处 | 摧毁 `02` 的分层依赖序（Foundation→Config→Workflow→Archi）+ `06` 的语义序（Views 在 Components 前） |
| `(from, to)` 字典序 | 17 处（14 处组内 `to`） | 摧毁「生成物中继边提前」这套排布 |
| `from` 组按元素声明序 | 5 处 | `02` 的关系组是字典序；两套惯例按文件分治（§2.3），统一即改写其中一方 |

结论：任何机械序都要一次改写既有产物的一半，且此后每次写都在跟人手排的语义序打架。
最小移动（§1.3）则对健康文件零动作——这是唯一与「每次写都跑一遍」相容的选择。

### 6.3 已知副作用（进 proposal 的「不含」或风险）

1. **一次字段修改可能夹带搬家**：首次写到 `06` 时，改一个 `api` 字段的 diff 会带 3 块搬迁。
   这是 E2 落地的必然产物，不是缺陷——`reordered`（§4.5）就是它的可见化手段。
2. **强约束**：有人为了阅读有意拆开子树，下次任何工具写都会合回去。这是不变量的本意，
   但要在知识面（骨架 ≤ 1500 B 的预算内）写清楚——见 §4.4，实际做法是删字而非加字。
3. **自由文本通道造出的违例无暴露面**：刻意如此（§6.1-b）。它不会报错、不会 warning，
   只会被下一次工具写静默修好；若长期不走工具写，违例就长期存在——可接受，因为此时
   diff 也只是"不整洁"，无任何功能后果。
4. **`06` 的 3 块搬迁无法避免**：E2 一旦落地，首次写到 `06` 必然触发。可选的是同批人工修好，
   但它本质上会由规范化自动完成，人工修只是让 diff 出现在一次专门的提交里。**建议人工修**
   （一次性 `06` 专项提交），这样首个功能 diff 不含夹带搬迁。
