## 关键设计决策

| # | 议题 | 定稿 | 理由 |
|---|------|------|------|
| D1 | 「追加失败静默」的载体与 `commit` 语义 | `LiveExec { exec_id: String, log_path: PathBuf, writer: Arc<Mutex<Option<std::fs::File>>> }`——**不新增布尔标记**：追加失败时把 `*guard` 置 `None`（`take` 掉句柄）即「内部失效」，后续 `append` 落空操作；`commit(&self, output: &[u8]) -> Result<String, String>` 先 `take` 句柄（关文件）再 `std::fs::write(log_path, output)`（覆盖），返回 `exec_id.clone()`。`commit` 后追加同样恒空操作（同一 `None` 语义，不需要第二状态） | 用「句柄在场 ⟺ 可追加」把 spec 的「失效标记 + commit 后空操作」两条并成一个状态位，状态数从 3 降到 2；`commit` 以同 `exec_id` 覆盖是 AC-2 的硬要求，`std::fs::write` 的截断语义天然满足「live 交错流被覆盖」 |
| D2 | `LiveSink` 与 `write_command` 的形态 | `#[derive(Clone)] pub struct LiveSink(Arc<dyn Fn(&[u8]) + Send + Sync>)`；`pub(crate) fn new(append: impl Fn(&[u8]) + Send + Sync + 'static) -> Self`、`pub(crate) fn absorb(&self, bytes: &[u8])`；`impl Debug for LiveSink` 手写 `"LiveSink(..)"`（`Arc<dyn Fn>` 不实现 `Debug`，而 `RunOptions` 派生 `Debug`）。`write_command(&self, command: &str) -> Result<(), String>` 为**原样追加**（`OpenOptions::new().create(true).append(true)`）：**不追加换行、不格式化、不改写**，分段与换行的组装责任在调用方 | 构造面 `pub(crate)` 使唯一生产路径是 `LiveExec::sink()`（不为尚未存在的消费者开公开构造）；`write_command` 不掺格式化——AC-3 要求 static-check 的 `.cmd` **逐字**等于 `"{static_analysis} 2>&1"`（含 `2>&1`、无尾随换行），若本方法自行补 `\n` 则该 AC 无解；test-exec 的多段格式由 `mod.rs` 单点组装（D4） |
| D3 | 增量读的字符边界算法 | `read_exec_output_delta_in(change_dir, exec_id, from_offset) -> Option<ExecOutputDelta>`：①`is_valid_exec_id` 失败 → `None`；②双锚 `find_map` 读整文件字节（`Ok(Vec)`，**空文件也是 `Ok`，与「文件缺失」天然可分**）；③`let len = bytes.len() as u64`；`from = if from_offset > len { 0 } else { from_offset as usize }`（收口覆盖变短 → 夹 0 重读，MUST NOT 返回空串）；④`let end = from + complete_prefix_len(&bytes[from..])`（**模块私有纯函数**：从尾部回看至多 3 字节，若落在未完成多字节序列内则退到该序列起点、否则返回全长；非法首字节按单字节计 ⇒ 以替换符呈现且游标越过）；⑤`text = String::from_utf8_lossy(&bytes[from..end]).into_owned()`、`next_offset = end as u64` | spec 逐条对得上：半字符留待下次（④的退位臂）、非法字节不卡游标（④的「非法首字节 = 1 字节」臂）、覆盖变短不越界（③）、空文件 `Some("")`（②的 `Ok` 分支）、`from_offset == 0` 即全量（③不退位时 `end == len`）。`complete_prefix_len` 为**纯函数零 IO**，边界规则集中一处，避免 `from_utf8` 的 `Utf8Error` 两臂（`valid_up_to` / `error_len`）在调用侧散开 |
| D4 | testexec「spawn 前写命令」的原料通路 | `execute_plan(plan, report_dir, cancel, live: Option<LiveSink>, on_command: Option<&(dyn Fn(&str) + Sync)>)`：`on_command` 在**裁决出最终命令串且 spawn 之前**被调用恰一次（`Keep` / `Omit` 两臂；`Reject` 臂零调用——零 spawn 即零新段）。`+ Sync` 是硬要求：`execute_plan` 返回的 future 必须 `Send`（`BoxToolFuture`），`&dyn Fn(&str)` 缺 `Sync` 界会使整体不 `Send`。`mod.rs` 侧传入的闭包做**全部格式化**：`\|command\| { let _ = live.write_command(&format!("\n=== plan {id} · {framework} ===\n{command}\n")); }`（`plan.id` / `plan.framework` 由 `mod.rs` 的循环变量供给）；`None` = 不关心命令文本（测试装置 / 未来消费者） | 命令串的展开与预算裁决的**单点在 `execute_plan` 内**（`ExpandMode` / `decide_argv` / `expand_template` 全在 `runner.rs`），外部无法复算而不复制一遍（spec 禁止两写）；记录生命周期（`begin` / `write_command` / `commit`）仍只在 `mod.rs`（spec Module Contract 明写 runner「MUST NOT 自持记录生命周期、MUST NOT 自写 `.cmd`」）。故只能是一条**只给命令文本、不带记录类型**的窄回调——`&(dyn Fn(&str) + Sync)` 而非 `exec::LiveSink`（后者的构造面 `pub(crate)` 在 exec crate 内，checks 侧无法构造） |

## 数据模型

### 磁盘面（本变更唯一的持久化演进：**新增两枚同目录文件，零表结构变化**）

```
<changes_root>/<change name>/reports/<test|baseline>/exec-outputs/
├── <exec_id>.log      ← 既有（内容口径零变）；本变更：运行中即在场且单调增长，收口同 id 覆盖为权威内容
└── <exec_id>.cmd      ← 新增 sidecar（纯文本 UTF-8，零 schema 治理，Q5 裁定）
```

| 项 | 口径 |
|----|------|
| `exec_id` | 形态零变：`exec-<millis>-<seq>`（`mint_exec_id` 一字不动）；进程内跨树唯一 |
| `.log` 正文 | 既有口径零变——static-check 为 `attempts_log(&run)`（单次尝试即 `stdout ++ stderr`）、test-execution 为「plan 分隔头 + 各 plan 合并输出」按 plan 序；运行中为 drain tee 的**真交错流**（stdout / stderr 按到达序），收口整体替换 |
| `.cmd` 正文 | static-check：**恰一条** `"{static_analysis} 2>&1"`（无尾随换行）；test-execution：**每已 spawn plan 一段** `\n=== plan <id> · <framework> ===\n<展开后的命令>\n`（plan 序，与 `.log` 的 plan 分隔头措辞同族可对读）；复用门零 spawn ⇒ 无 `.cmd`（`None`） |
| 清理由谁 | 无人（既有「无 GC」语义）；runner 只清 `reports/test/<plan>` 子目录，不触 `exec-outputs/` ⇒ live 文件不会被误删 |
| 双锚探测 | 三只读函数（command / delta / log 路径）与 `read_exec_output_in` 同口径：`Test` 槽先、`Baseline` 槽后，首中即返 |

### 内存面（运行期状态机，无持久化）

```
LiveExec
├── exec_id: String                    铸造即定；commit 返回同值（同 id 收口的物理载体）
├── log_path: PathBuf                  布局派生（exec_output_dir_in + "<exec_id>.log"）
└── writer: Arc<Mutex<Option<File>>>   Some = 可追加（append + flush）；None = 失效（追加失败 或 已 commit）
                                       ⇒ 「失效标记」与「commit 后空操作」共用一个状态位（D1）

StepEmitter（'static，跨 port 边界）
└── (key: (root, change_id), control: Arc<ChangeFlowControl>)
     └── attach_output_ref(phase, attempt, step, instance_no, exec_id)
           → 临时 RunGuard{key, control} → emit_node(Running + output_ref)
           → ChangeFlowControl::publish → accumulate_node（output_ref some ⇒ 覆写；started_at 保首见；节点数不变）

前端 useExecOutput
├── offsetRef.current: number          唯一来源 = 后端 nextOffset；臂变化（root/changeName/execId/status）时归 0
├── pendingRef.current: boolean        同臂单飞标记（D10-a）：true = 一次增量读在飞 ⇒ 新到请求只置 queuedRef，不叠读
├── queuedRef.current: boolean         在飞期间的排队标记：结算后折成至多一拍尾读（有界链，不随信号数增长）
├── text: string | null                累积态：null = 尚未取到（空态）；'' = 已取到但 0 字节（运行中等）
└── command: string | null             命令头行（一次读；失败不阻断 text）

StdoutPanel
└── stickRef.current: boolean          粘底标志（isStuckToBottom 判定；上滑即 false，回底恢复 true）
```

**不变量**：

| 状态 | 初值 | 不变量 |
|------|------|--------|
| `writer`（`LiveExec`） | `Some(File)` | 一经 `None` 永不复位；`None` 后 `sink` 的追加恒空操作（续跑语义不回来）。`write_command` **不共用**该句柄——每次以 `OpenOptions::create(true).append(true)` 自开自关，故不受 `writer` 状态影响，失败只返回 `Err` 由调用方 `.ok()` 静默降级 |
| `offsetRef` | `0` | `next_offset` 单调不减且 `<= 文件长度`（后端保证）；前端不自行计数 ⇒ 不出现「JS 字符数 vs UTF-8 字节数」分裂 |
| `pendingRef`（`useExecOutput`） | `false` | 同臂同一时刻**至多一次**增量读在飞（D10-a 的入口短路）；`true` 时新到请求一律不叠读、只置 `queuedRef`。结算顺序硬约束：**先**清 `pendingRef` **再**推 `offsetRef`（否则尾读会用旧游标抢跑）。臂切换（effect 实例更替）与 cleanup 一律归 `false` |
| `queuedRef` | `false` | 只在 `pendingRef === true` 时被置真；结算（`then` / `catch`）末尾读取并清零，命中即补**一拍**尾读 ⇒ 队列长度恒 ≤ 1，不随信号频率累积。`disposed` 分支不清标记（ref 随 effect 实例作废） |
| 节点 `output_ref` | `None` | running 拍与终态拍**同值**（同 `exec_id`）；`accumulate_node` 的「some 才覆写」使补发拍只补字段、不新增节点、不动 `started_at` |
| `stickRef` | `true` | 只在 `onScroll` 与文本变化 effect 内读写；组件卸载即失效（不持久化） |

**关系**：一条 `LiveExec` ⟷ 一个 `exec_id` ⟷ 一个 `.log` + 一个 `.cmd`（1:1:1，均由 `begin` 一处铸造）；一个 watch 订阅 ⟷ 一个 `status === 'running'` 的前端臂（1:1，由 `armKey` 保证）；一个 run 步节点 ⟷ 一个 `output_ref`（0..1，`run_tool` 仅在位时上抛）。

**持久化**：`RunNodeRecord` / bincode v1 **零改动**（`output_ref` 字段本就在案，running 拍与终态拍同值）；命令文本走 sidecar 而非节点行，正是为守住「bincode version bump + 升级链」这条代价（proposal「零改动的能力」表）。

## 待决问题

1. **`testexec` 的 `begin` 位点（D5）与 proposal §3 字面的差异**：proposal 写「`begin` 在 detect 之前」，本设计放在 detect 成功之后（理由：detect 的显式 `Err` 不留孤儿空记录）。若评审坚持字面顺序，改法是把 `begin` 上移一行、并接受「detect `Err` 时留下 0 字节永不 `commit` 的 `.log`，且已上抛的 `output_ref` 指向它」——**两种都不违反 spec 的顺序不变量**，此处取偏离更小者。
2. **`read_exec_output` 体内改为调用私有 `change_dirs`（D8）**：接口 / 语义 / 生成物均零变，但源码不再是「一字不动」。若评审要求字面保留，则新三命令必须各写一份定位（违反 spec「不另写第二份定位逻辑」），故取抽取。
3. **新增 `flow/stdout-text.ts`（D9）**：proposal 的「实现文件」表未列此文件。理由是不新增就无法同时满足「纯函数可直测」与 knip 的 `Unused exports` 判据（AGENT.md 规则 5 禁 test-only 导出）。落点在既有 `Views.Changes.Flow` 的目录 path 内 ⇒ 架构模型零改动。
4. **`useExecOutput` 导出面去掉 `loading`**：`stdout-panel.tsx` 的「加载中…」态随之退场（等待态改由 `status` 承载）。既有 `use-exec-output.test.ts` / `stdout-panel.test.tsx` / `detail-drawer.test.tsx` / `change-detail-view.test.tsx` 中依赖 `loading` / `read_exec_output` 的断言需要改写——判据与改写归测试相位，本设计只声明「API 面变更」这一事实。
5. **`write_command` 的侧车追加换行归属（D2 / D4）**：static-check 的 `.cmd` 无尾随换行（AC-3 逐字），test-exec 的段间换行由 `mod.rs` 组装（`\n=== … ===\n<command>\n`）。两者形态不同是刻意的（单一命令 vs 多段清单）；若后续出现第三种消费方，MUST NOT 把格式化下沉进 `write_command`（那会破坏 AC-3 的逐字口径）。
6. **`ExecOutputDelta.next_offset` 的类型面**：`u64` 出线为 TS `number`（既有 `dangerously_cast_bigints_to_number` 口径）。日志长度上界受 2^53 约束（实际远小于此），本变更不引入 `BigInt` 面；若将来出现超长日志（> 8 PB 量级，不可达），需要重估。
7. **AC-15 的「`mutation/**` 零 diff」与 `RunOptions.live` 必填字段的冲突**：proposal §2 明写「4 处生产构造点……后两者补 `live: None`」，而 AC-15 又把 `crates/infra/checks/src/mutation/**` 列进零 diff 面——两者不能同时字面成立（`RunOptions` 不提供 `Default`、`live` 无缺省，缺字段即编译失败）。本设计按 §2 执行：mutation 两文件各补一行 `live: None`，`MutationRunner::run` 签名与其段内行为零改动（Q2「不纳入」的实质不受影响）。若评审要求字面零 diff，唯一出路是给 `RunOptions` 加 `Default`——那会打破「`timeout` 必填、无超时 spawn 在类型层不可表达」的既有红线，故不取。
8. **`StepEmitter` 构造临时 `RunGuard` 的做法（D6）**：`RunGuard` 只是 `(key, control)` 两字段的 `'static` 包，构造零成本、零注册表副作用；若评审倾向「给 `emit_node` 加 `(key, control)` 变体」，则铸造点仍是单点、调用面会多一个重载——本设计取「复用同一函数签名」这条更窄的路。
9. **阶段切分调整（D15 / 回溯原因 ① 的修法）**：初稿把 `OutputRefSink` 类型面拆在「阶段二（checks）」与「阶段三（core 上抛）」两侧，导致阶段二结束时工作区不可编译（`port.rs` 的 trait 未扩参而 checks 侧 `impl` 已扩参，或反之），阶段二/三无法各自验证。现改为：类型面（含两 trait 扩参、两 `impl` 扩参、`steps.rs` 透传、14 处测试 `impl` 适配（生产 2 处由本阶段一并扩参）、33 处 `ToolStepRequest` 字面量 + 1 处穷尽解构补字段）独立成阶段二且**零消费**，`infra/checks` 的记录链接入退为阶段三、emit 上收退为阶段四。代价是阶段二没有可观察行为变化（纯签名 + 编译面），收益是每阶段结束工作区都可编译、可独立验证。
10. **`run_tool` 调用点计数（回溯原因 ② 的修法）**：初稿记「12 处（4 `Some` + 8 `None`）」，实测 **14 处**——漏了 `drive` 内的归档 preflight（`:281`）与 `step_mutation_test_escalate`（`:1402`）。两者都必须补 `None`（`identity: Option<StepIdentity>` 是末位必填形参、无缺省），漏改即编译失败。同理本项目实测的其它计数：两 runner trait `impl` 共 16 处、`ToolStepRequest` 字面量 33 处、`static_check_test.rs` 的 `.run(..)` 是 5 处（非 6 处）、`testexec/mod_test.rs` 15 处 `.run(..)` + 6 处 `execute(..)`、`runner_test.rs` 46 处 `execute_plan(..)` + `detect_test.rs` 1 处——阶段任务按这些实数列出，避免再以估计值驱动涟漪清单。
11. **`OutputRefSink::new` 的可见性（D16，回溯补正 A）**：原稿定 `pub(crate)`，判据「唯一生产路径 = `walker::run_tool`」。该判据只覆盖生产面：checks crate 的记录链用例需要构造 `OutputRefSink` 才能断言「上抛 1 次 / 上抛时刻文件已在 / 缺省面零调用」，而唯一构造面在 orchestration 内部 ⇒ **checks 侧结构性不可写**（原 test-design 只能全传 `None` 并在注释里说明缺口，重跑必再失败）。**裁定：转 `pub`**。代价是公开面多一个构造函数（已存在类型的构造口，非新抽象）；收益是 AC-11 的两条断言在 checks 侧可写。对称面：`LiveSink::new` 保持 `pub(crate)`（D18）——checks 侧有 `LiveExec::sink()` 这条公共取得路径（`runner_test.rs:3874` 已按此实现），无跨 crate 直构需求。
12. **AC-11 组合落点（D17，回溯补正 B）**：「真实 `ProcessStaticCheck` + 真实 `RunGuard` 上抛链」的端到端用例原计划落 `walker_test.rs`，但那要求 `crates/core/orchestration` 加 `checks-runtime` **dev-dependency** ⇒ core → infra 反向边，违反依赖方向且产生 archi `undeclaredDependency`（模型里只有 `ChecksRuntime → Core.Orchestration` 的正向边）。**裁定：落 `src-tauri/src/commands/change_flow/mod_test.rs`**（壳层同时依赖双侧，且已有「组合根装配」先例）。`crates/core/orchestration/Cargo.toml` 零 diff 成为可机械审查的判据。walker 侧自身的上抛覆盖退到「假 runner 回调」面（`walker_test.rs` 用可编程 mock runner 在 `run` 内 `emit`，不需要 checks crate）。
13. **`on_command` 的 `Reject` 臂在非 Windows 不可达（测试可达性留痕）**：`runner.rs:35` 的 `line_budget()` 在 `#[cfg(not(windows))]` 返回 `None`，而 `decide_argv` 首句 `let Some(budget) = budget else { return Keep }` ⇒ unix 上 `execute_plan` 恒 `Keep`，「`Reject` 臂 `on_command` 零调用」的**端到端**用例只能在 Windows 上断言。两条可行路径（判据与改写归测试相位）：① 该端到端臂 `#[cfg(windows)]`；② 改为对 `decide_argv` 直测（同 crate 可见、`budget` 为显式入参，非 Windows 上亦可传 `Some(0)` 逼出 `Reject`），并把「`on_command` 零调用」用 `Keep` / `Omit` 两臂的日志对照锁定。本设计**不改** `line_budget` 的平台门控（那是既有设计）。同类留痕：`plan.id` 由 `checks::aggregate::derive_plan_id(root, framework)` 派生（`\\` / `/` → `_`），「含 emoji 的 plan id」不经 `detect`——用例侧以手工构造 `TestPlan` 提供（`runner_test.rs` 既有 `unsafe_plan` / `filler` fixture 同型先例）。
14. **前端函数覆盖缺口的承接方式（D19 / D19-a，回溯补正 · 覆盖口径）**：`reports/test/packages_desktop_vite-plus/coverage-summary.json` 实测 `functions` 1824/2031 = 89.80%（阈 90%），分母较基线的 1957 增 74，其中 43 个来自本变更首次 import `@/components/ui/code-block` 时被其两条**静态再导出**带进 import 图的 vendored 子树（`lib/highlighter.tsx` 22 函数 / `hooks/use-highlighted-code.ts` 6 函数 / `code-block.tsx` 15 函数），达标只差 4 个函数。**裁定：拆窄模块**（`code-block-copy-button.tsx`，原样搬出 `CodeBlockCopyButton`），`stdout-panel.tsx` 从窄模块 import ⇒ 三文件整体离开 import 图、`vite.config.ts` 的 `coverage.exclude` 与 `openspec/config.json` 阈值**零 diff**。否决的两条路与其代价：① 剔分母（`coverage.exclude`）——`vite.config.ts` 不在变更清单内，且仓库既有裁定明禁「以调阈值 / 剔分母替代用例」，并会连带失去 `code-block.tsx` 真实执行面的观测；② 为 shiki 补测试——`src/components/ui/**` 同时是 `stryker.config.json` 的 mutate 排除面与 `openspec/config.json` 的 `tests[].excludes` 圈定外区（三处豁免一致），本仓从不为它备测试投入，补 shiki 夹具属「为分母写测试」。**留给 test 相位的两条注意**：① `code-block.tsx` 的再导出（`CodeBlockCopyButton` / `useHighlightedCode` / `highlightCode`）**MUST NOT 被删**，将来若有生产消费方 import barrel，同型覆盖缺口会重现——届时应把该消费方也指向窄模块，而不是给 vendored 树补测试；② 窄模块自身的覆盖由 `stdout-panel.test.tsx` 的真实渲染路径提供（拆分前后该文件都断言复制按钮点击 → `navigator.clipboard.writeText`，无需新增用例；反映在单跑里是 7 函数 6 覆盖，未覆盖的 1 个是 `onClick` 缺省分支的 `onClick?.()` 短路臂）。**spec 侧零 delta 改动**：`specs/desktop-change-flow-view/spec.md` 的 Module Contract 只写「复用既有 `CodeBlockCopyButton`」、未钉 import 源与文件位置，故 D19 的拆分不构成契约漂移（组件本身仍是既有那个、行为逐字不变）；同一判断适用于 `specs/desktop-app-shell/spec.md` 的「全管线无豁免」（新文件照常过 fmt / lint / knip，未新增任何 ignorePatterns）与 `specs/repo-archi-model/spec.md` 的「`src/components/ui/` 收敛为 1 元素」（新文件落在既有目录 path 内，零模型改动）。

15. **同臂双读的单飞守卫（D10-a，回溯补正 · 前端跟随）**：D10 原稿的 `readDelta` 只裁决「`chunk === null` 忽略 / `text === ''` 不 setState」，**未处理「一次读在飞时又来一次」**。缺口是结构性的、不是偶发竞态：① `useFileWatchSignal` 的 500 ms 是 **trailing 防抖**，它只合并**信号**，对**已发出的读**毫无约束；② 后端 `read_exec_output_delta_in` 是整文件 `std::fs::read`（`crates/infra/exec/src/lib.rs:365-389`，体内 `std::fs::read` 在 `:376`）——文件越大耗时越长，而运行中日志可达 MB 量级；③ 装载首拍 `readDelta()` 与首个防抖信号只隔 500 ms，两者极易叠；④ 无守卫时两次读用**同一个** `offsetRef.current` 发出 ⇒ 后端两次都返回「自同一游标起的同一段文本」（后端是**无状态快照**语义，幂等）⇒ `setText(prev => prev + chunk.text)` 把同段**追加两遍**（破 AC-4「连续增量拼接 == 全量」），且两次写入的 `nextOffset` 相同（破 AC-6 的「offset 推进」可断言性）。**裁定：入 `pendingRef` 短路 + `queuedRef` 排队一次 + 结算后清标记 + 至多一拍尾读**（D10-a 三条规则）。为何不是纯丢弃：一次在飞读的快照早于新信号，纯丢弃会让该信号的增量在「此后进程静默到收口」的情形下**永久丢失**；为何不是每信号一拍：增量读是「全量快照 + 游标」，尾读一拍即吃掉其间全部字节，队列长度恒 ≤ 1 即足以保持正确性且不给 IPC 面加压；为何不下沉 `useFileWatchSignal`：共享件 spec 明写「零取数」，且第二消费方 `use-explore-doc` 是整读幂等（无需单飞）——下沉即为一个消费方的语义给另一个消费方加约束。**副作用留痕**：`readDelta` 的行数随之增加（守卫 4 行 + 尾读 2 行），`useExecOutput` 主体仍在 `max-lines-per-function` 50 行内（挂 watch 的调用与三 effect 分属 `useCommandText` / `useOutputText` 两个模块私有 hook，见「变更清单 · 修改文件」）。**用例要求（归 test-design / test-gen，本轮必须由 test-design 显式列出，否则代码不修则无从验证）**：`use-exec-output.test.ts` 至少三臂——① **同臂双读折叠**：`readExecOutputDelta` 以**可控 deferred** 挂起第一拍，期间触发两次 watch 信号（推进 500 ms 各一次），断言在飞期间 `readExecOutputDelta` **仍只调用 1 次**、`fromOffset` 不前进；完成后断言总调用 **2 次**（1 拍在飞 + 1 拍尾读合并两次信号）且第二拍的 `fromOffset === 第一拍的 nextOffset`；最终 `text` 与全量**逐字相等**（不重复追加）、`nextOffset` **严格递增**。② **尾读有界**：在飞期间触发 **5 次**信号 ⇒ 尾读仍只补 **1 拍**（总调用 2 次），断言「队列长度恒 ≤ 1」。③ **reject 后仍可续读**：第一拍 reject ⇒ `error` 置串、`pendingRef` 清位；随后一次信号触发的新读**正常发出**并成功追加（断言 `pendingRef` 未卡死成永久真——这是守卫最危险的失效形态）。三臂均以「同臂双读」命名，便于回溯原因追到 D10-a。**spec 侧零 delta 改动**：`specs/desktop-change-flow-view/spec.md` 的「跟随语义」只钉「信号到达后再取一次增量、游标推进」与「`offset` 唯一产出方在后端」两条口径，单飞守卫是**满足该口径的实现细则**（无守卫则口径在并发下不成立），既未新增契约面、也未收窄消费者；spec 的 Module Contract 一行补注归规格相位，本设计只在 D10 / D10-a 与 `tasks.md` 阶段七落地。
