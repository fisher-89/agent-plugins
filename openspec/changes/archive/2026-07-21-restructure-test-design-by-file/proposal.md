# 提案: restructure-test-design-by-file

> **变更**: restructure-test-design-by-file
> **日期**: 2026-07-21
> **状态**: draft

---

## 问题

当前 `test-design.md.template` 的测试设计存在三个结构性缺陷：

1. **单元测试与集成测试边界模糊**：模板未明确区分两类测试的关注域。单元测试用例和集成测试场景共享相同的表格结构，缺乏对各自特有维度（单元测试→函数级分支；集成测试→跨模块交互）的差异化表达。

2. **集成测试缺少跨模块交互的显式声明**：集成测试场景分散在 `### 用例` 的大表格中，未显式声明场景涉及哪些模块、模块在交互中承担什么角色。审查者无法快速判断一个集成测试是否真正跨了模块边界。

3. **单元测试表格数据跨章节分散**：所有文件的测试用例在一个大表（`### 用例`），所有文件的 Mock 策略在另一个大表（`### Mock策略`）。审查者查看一个文件的完整测试设计时，需要在两个章节之间反复跳转，无法获得对单个文件测试全貌的一览式呈现。

4. **缺少待测内容的概览信息**：单元测试缺少"待测功能"的显式描述，集成测试缺少"待测关系"的描述。审查者无法快速了解每个文件/每个交互域具体覆盖了什么内容。

5. **分类框架存在固有问题**：上一版尝试将集成测试关系分为"数据关系/时序关系/逻辑关系"三个固定分类，但探索阶段的实践表明——有意义的跨模块交互同时涉及数据流动、时序约束和涌现逻辑，强制分类本质不可判定。需要更灵活的组织方式。

---

## 提案

将 test-design.md 从**按表格类型分组**改为**按被测单元分组**，每个被测单元章节自包含。

### 单元测试：按源文件分组

1. **模板重组**：`### 用例` / `### Mock策略` 的全局表格 → `### <源文件> -> <测试文件>` 的 per-file 分组
2. **新增"待测功能"**：每个文件章节下新增 `#### 待测功能` 小节，用列表列出被测函数及简短描述
3. **简化表格列**：`#### 用例` 和 `#### Mock策略` 表格去掉 `测试文件` 列（已在 heading 中表明）

### 集成测试：按自由命名的关系分组

集成测试聚焦**跨模块交互**，而非模块内部逻辑。单元测试通过 Mock 策略已覆盖模块依赖关系（mock 真实内部模块 = 隐式验证了接口契约），集成测试不应重复验证依赖关系。集成测试应聚焦模块组合时才暴露的行为。

**放弃按关系类型分类**。上一版将关系分为"数据关系/时序关系/逻辑关系"，但真实场景中这三者是同一交互的不同视角——任何有意义的跨模块交互都同时涉及数据流动、时序约束和涌现逻辑，强制三选一本质不可判定。改为自由命名的关系标题，让 planner 用自然语言描述交互。

### 集成测试模板结构


### 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 顶层分组维度 | 自由命名关系标题 | 规避分类歧义；planner 用自然语言描述交互，无需纠结归类 |
| 测试文件粒度 | 每组关系一个测试文件 | 测试文件在关系标题中声明（`→ test.ts`），与单元测试 `源文件 → 测试文件` 形成对称 |
| 涉及模块 | 表格（模块+角色） | 强制显式声明跨模块性；审查者一眼看到交互边界 |
| 场景描述 | 自由文本段落 | 叙事比清单更能表达意图；planner 被迫解释而非填表 |
| 路径类型位置 | 用例表内列 | 一个场景覆盖多个路径类型，减少场景数量；与单元测试用例表的 `路径类型` 列对齐 |
| Mock策略范围 | 仅跨进程边界 | 内部模块间调用已在单元测试中通过 Mock 验证 |
| 关联AC | 关系级元数据 | AC 是关系级的，不需要每个场景重复 |
| 前置条件 | 场景描述中自然表达 | 不是每个场景都需要显式前置条件 |

### Evaluator T8 检查逻辑

集成测试部分的结构检查变为纯语法检查（无需语义分类判断）：

- 每个 `###` 标题包含 `→ test_file_path` 模式
- `**涉及模块**` 表格存在且 ≥2 行（保证跨模块性）
- `**关联AC**` 非空
- `**关系描述**` 段落非空
- 至少一个 `#### 场景: ...`
- 每个场景有 场景描述文本 + `##### 用例` 表格
- 用例表列名: `路径类型 | 测试条件 | 迭代类型`
- Mock策略表列名: `Mock主体 | Mock方案 | 应用场景`（或标注无Mock）

## 能力

### 新增能力

- **test-design-template** — 定义 `test-design.md.template` 的结构格式：单元测试按 per-file 组织（`### 源文件 -> 测试文件`），集成测试按自由命名的关系标题组织（`### 关系标题 → 测试文件`），每项关系包含涉及模块表格、关联AC、关系描述段落、场景级用例和 Mock 策略
- **test-design-planner-workflow** — 定义 test-design-planner agent 的生成逻辑，包括 per-file 单元测试章节生成、自由命名关系标题的集成测试章节生成、test_resolve_paths 和 test_detect_frameworks 的集成
- **test-design-evaluator-workflow** — 定义 test-design-evaluator agent 的检查逻辑，尤其是 T8 格式检查对新模板结构的适配，包括自由命名关系标题、涉及模块表格、关联AC、关系描述、场景级用例和 Mock 策略的语法验证

## 风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 自由命名关系标题导致标题风格不一致，关系边界模糊 | 不同 PR 的 test-design.md 风格不统一，增加审查认知负担 | 中 | 模板注释给出命名建议（"CLI参数 → eval.json持久化" 的箭头链路格式）；planner Process 中加入命名指南；evaluator 检查 `→ test_file` 模式的存在性 |
| 下游 test-gen 解析受影响 | test-gen 无法提取集成测试场景数据 | 低 | 关系标题虽改为自由命名，但场景内容仍使用标准 `##### 用例` 表格格式（列名不变）；test-gen 按列名读取，不受 heading 层级变化影响 |
| 场景描述段落长度失控 | 审查者需要阅读大段文本才能理解场景意图 | 低 | 模板注释给出段落结构建议（验证什么 + 前置条件 + 输入和预期输出）；planner Process 建议段落简洁 |

## 过程

### 决策

| 问题 | 决策 | 理由 | 备选方案 |
|------|------|------|----------|
| 集成测试顶层按什么维度分组？ | 自由命名关系标题 | 分类框架（数据/时序/逻辑）在真实场景中不可判定；planner 用自然语言描述交互，无需纠结归类 | 按关系类型（数据/时序/逻辑）——分类歧义高，本质不可判定；按场景分组——缺少跨模块边界的显式声明 |
| 集成测试场景 Mock 策略的范围？ | 仅跨进程边界 | 内部模块间调用已在单元测试中通过 Mock 验证；重复 Mock 增加维护负担 | 所有外部依赖都 Mock——冗余；不 Mock——测试不稳定 |
| 集成测试的用例表是否保留 `测试文件` 列？ | 不保留 | 测试文件已在关系标题中声明（`→ test_file`），列冗余 | 保留——冗余信息 |
| 集成测试的用例表是否保留 `场景描述` 列？ | 不保留，改为场景级段落 | 叙事比清单更能表达意图；场景描述段落 + 用例表的分工比单一大表更清晰 | 保留为列——表格单行空间不足，长描述被截断 |
