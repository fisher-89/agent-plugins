## 第一阶段：模板重组

此阶段重写 test-design.md.template，是整个变更的基础。模板结构确定后，planner 和 evaluator 的修改才有参照对象。

- [x] 1.1 重写 `plugins/dev-team/templates/artifacts/test-design.md.template` 的 `## 单元测试` 章节
  - 将全局 `### 用例` / `### Mock策略` 扁平结构替换为 per-file 分组模板
  - 新增重复章节模板：`### {{源文件}} -> {{测试文件}}`
  - 每个 per-file 章节按顺序包含：
    - `#### 待测功能` — 使用无序列表格式（`- funcName(): 描述`）
    - `#### 用例` — 表格列：`测试对象 | 路径类型 | 测试条件 | 迭代类型`（不包含 `测试文件` 列）
    - `#### Mock策略` — 表格列：`Mock主体 | Mock方案 | 应用场景`（不包含 `测试文件` 列）
  - 在 `#### 待测功能` 后添加 HTML 注释，说明列表格式和内容来源
  - 在 `#### 用例` 后添加 HTML 注释，说明新列定义
  - 在 `#### Mock策略` 后添加 HTML 注释，说明新列定义（无测试文件列）

- [x] 1.2 重写 `plugins/dev-team/templates/artifacts/test-design.md.template` 的 `## 集成测试` 章节
  - 将全局 `### 用例` / `### Mock策略` 扁平结构替换为 per-relationship 分组模板
  - 新增重复章节模板：`### {{关系标题}} → {{测试文件}}`
  - 关系标题为自由命名，模板注释给出命名建议（箭头链路格式，如 `CLI参数 → eval.json持久化`）
  - 每个关系章节按顺序包含三个元数据元素：
    - `**涉及模块**` 表格—列名 `模块 | 角色`，模板注释要求 ≥2 行
    - `**关联AC**: AC-1, AC-2` 行
    - `**关系描述**:` 叙事段落
  - 每个关系章节包含至少一个 `#### 场景: {{场景名称}}` 子章节，每个场景包含：
    - 叙事描述段落（验证什么 + 前置条件 + 输入 + 预期输出）
    - `##### 用例` 表格 — 列名 `路径类型 | 测试条件 | 迭代类型`
    - 可选 `##### Mock策略` 表格 — 列名 `Mock主体 | Mock方案 | 应用场景`（仅跨进程边界，模板注释说明规则）
  - 在 `## 集成测试` 章节开头添加 HTML 注释，说明集成测试与单元测试的边界

- [x] 1.3 确认 `## 验收范围` 和 `## 不可测试项` 章节保持不变
  - 验证 `## 验收范围` 表列名保持 `AC ID | 验收条件 | 测试类型 | 测试文件 | 测试对象/测试场景`
  - 验证 `## 不可测试项` 格式不变

- [x] 1.4 整体验证模板结构一致性
  - 确认单元测试部分无残留的全局 `### 用例` / `### Mock策略`
  - 确认集成测试部分无残留的全局 `### 用例` / `### Mock策略`
  - 确认所有表格列名与 proposal 中定义的 AC-4 一致
  - 确认所有新增/修改的章节均有 HTML 注释说明格式规则

## 第二阶段：Planner Agent 更新

此阶段更新 test-design-planner.md 的 Process 和 Output 指令，使其生成逻辑与第一阶段的新模板结构一致。

- [x] 2.1 更新 `plugins/dev-team/agents/test-design-planner.md` 的 Process 步骤
  - 保留 Step 6（模块列表汇总）和 Step 7（test_detect_frameworks）不变
  - **重写 Step 8**：从 "识别需要集成测试覆盖的场景，在每个 `__tests__/<scenario>/` 下创建测试用例" 改为：
    1. 从 proposal.md / design.md 识别跨模块交互
    2. 为每个交互生成自由命名的关系标题（使用 `→` 箭头链路格式）
    3. 对每个关系，确定涉及模块（≥2个）及其角色 → 生成 `**涉及模块**` 表格
    4. 列出关联的 AC-ID → 生成 `**关联AC**` 行
    5. 撰写关系描述 → 生成 `**关系描述**` 段落
    6. 对每个关系生成一个或多个 `#### 场景:` 子章节，每场景包含叙事描述 + `##### 用例` 表 + 可选 `##### Mock策略`

- [x] 2.2 更新单元测试路径映射逻辑
  - 将 Step 9-10 的 test_resolve_paths 调用和 `unit_tests` 映射逻辑从 "填充全局 `### 用例` 表" 改为 "为每个 `source -> test_file` 对创建 `### <source> -> <test_file>` 章节"
  - 新增：对每个 per-file 章节，grep 源文件导出函数/类签名 → 填充 `#### 待测功能` 列表
  - 新增：映射到 `#### 用例` 表时去掉 `测试文件` 列
  - 新增：映射到 `#### Mock策略` 表时去掉 `测试文件` 列

- [x] 2.3 更新 Step 11（不可测试项）— 不变
  - 确认 `test_resolve_paths` 返回的 errors 仍记录到 `## 不可测试项`

- [x] 2.4 更新 Step 12-14（模板读取和写入指令）
  - Step 12: 更新为 "Read `plugins/dev-team/templates/artifacts/test-design.md.template`，逐节确认新结构的占位符与内容来源"
  - Step 13: 更新为 "分段写入 test-design.md：先 `## 验收范围`，再逐文件写入 `## 单元测试` 的 per-file 章节，再逐关系写入 `## 集成测试` 的 per-relationship 章节，最后 `## 不可测试项`"
  - 每写入一段后对照模板确认列名和占位符无遗漏

- [x] 2.5 在 Constraints 中新增集成测试关系标题命名指南
  - 建议使用箭头链路格式（如 `CLI参数 → eval.json持久化`）
  - 关系标题应描述交互方向而非固定类型分类
  - 同一关系下场景名需唯一，跨关系不强制
